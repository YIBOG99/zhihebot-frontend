# 数据库迁移审计与首次部署风险

## 结论

**当前不能安全地指导新项目把 `migrations/` 里的所有 SQL 按文件名一次性执行。** 这些文件不是一个经过验证、可从零开始一键执行的 Supabase migration chain。此审计仅检查了仓库文件内容，没有连接或修改任何 Supabase 项目。

## 已确认的风险

1. **重复文件不是都可重复执行。**
   - `20260920_153000_daily_stats.sql` 与 `20260920_153728_create_daily_stats.sql` 内容重复；两者都创建同名策略，第二次执行可能因策略已存在而失败。
   - `20261005_000000_create_order_captcha.sql` 与 `20261005_184516_create_order_captcha_challenges.sql` 都定义验证码表/清理函数；虽然表使用 `IF NOT EXISTS`，后续授权/策略操作仍需核查。
   - `order_create`、`order_set_payment_method`、钱包和支付函数的文件是逐次演进版本，不应把中间版本当成独立功能版本随意跳过或乱序应用。

2. **部分迁移依赖之前已存在的对象。**
   - 商城表依赖 `profiles`；角色/权限函数依赖 `app_role`、`user_roles` 和 `has_role`。
   - 下单函数后续版本引用验证码、黑名单、推荐奖励、钱包、订单过期字段、费率字段等对象。只执行“看起来核心”的几个文件也可能造成函数创建失败或前后端字段不匹配。

3. **基础建表文件并非全幂等。**
   - 初始角色迁移使用 `CREATE TYPE`、多处 `CREATE TABLE` 与 `CREATE POLICY`，重复执行会失败。
   - 多个后续文件直接 `CREATE POLICY`，没有先删除同名策略；不能假设整目录可以反复运行。

4. **种子数据含有需要确认的旧配置。**
   - `20260920_075249_seed_faqs_coupons_settings.sql` 写入了旧的支付宝/USDT/微信收款展示信息、客服联系方式和旧站点公告域名。
   - 商品种子引用外部图片 CDN。
   - 不要把这些收款值当成新店铺已验证的真实收款信息。正式开放下单前必须在新项目中逐项核对并替换；未确认前不要开放收款。

5. **数据库就绪不等于支付就绪。**
   - 代码中存在支付/对账相关 RPC 与 Edge Function，但真实收款仍需要匹配的商户凭据、回调配置、服务端验签、幂等与异常订单测试。
   - `boss-api` 需要服务端 secrets；service-role key 不可写入任何 `VITE_*` 变量。

## 当前推荐的安全操作

- 暂时不要在新 Supabase 项目里执行整目录 SQL。
- 先确认该项目是空库，且没有需要保留的数据。
- 后续应生成一份**单独的、经过依赖核对的首次初始化脚本**，只保留每个对象的最终定义；脚本应按依赖顺序建立 schema、函数、RLS 和必要的种子数据，并把旧支付/站点配置改为安全占位值。
- 对初始化脚本做静态检查并在可丢弃的测试 Supabase 项目执行成功后，才用于正式项目。
- 初始化完成后，再部署 Edge Functions、设置 secrets、创建管理员并验证各后台页面。
- 在完成订单、支付回调、卡密发放和 RLS 的端到端测试前，保持快照模式/维护状态，不要接真实订单。

## 审计范围与限制

已检查初始角色/商城表、RLS/RPC、种子数据、日统计、验证码、订单创建/支付、钱包和频控相关迁移的若干代表版本，并确认存在上述冲突模式。尚未在真实 PostgreSQL/Supabase 实例中执行，因此本文不是“迁移全部通过”的声明，也不应被当成已完成的数据库部署。


## 补充：订单链必须按最终定义审查

进一步抽查订单相关 SQL 后，确认不能仅凭“创建表”与“函数”分类来挑文件：

- `order_create` 的签名先后增加优惠码、验证码、支付方式、充值标记等参数；较晚版本还加入黑名单、频控、白名单、手续费与充值订单分支。
- `20261005_210400_order_create_fee.sql` 的函数声明中曾将读取 JSONB 设置的变量声明为 `RECORD`，但函数体使用 `->>` 运算符；随后 `20261006_043000_order_create_jsonb_var_fix.sql` 才将其修正为 `JSONB`。若按时间顺序执行，必须确保最终修复版最后覆盖旧定义。
- `order_set_payment_method` 先有两参数版本，随后为了游客单增加查询密码摘要参数，并明确删除旧签名；遗漏最终版本会导致游客支付方式选择失败或 RPC 签名不匹配。
- 钱包、手续费、支付方式与频控迁移共享 `orders` 的字段和 RPC 签名。只执行部分迁移可能出现“前端请求字段与数据库函数不匹配”的运行时错误。

这类问题必须在一个可丢弃的测试数据库里做完整初始化与 RPC 冒烟测试，不能仅靠 SQL 静态阅读宣称已通过。

## 补充：构建配置仍有可独立化的遗留项

`vite.config.ts` 仍尝试从环境变量 `MEOO_SOURCE_LOCATION_PLUGIN_PATH`、`/app/sdk` 目录及 `@ali/oneday-agent-sdk` 查找一个可选的源码定位 Babel 插件。它被写成可选项，缺失时理论上不会阻止构建，但这仍是导出工程遗留的路径探测。独立化时可以移除该可选插件探测，保留标准 Vite React、Tailwind、TanStack Router 与 tsconfig-paths 插件；变更后仍应运行构建和类型检查确认。

## 补充：Edge Functions 独立部署审查

静态检查了仓库中的 Edge Functions 源码（未部署、未调用生产接口）后，还发现以下上线阻塞项：

1. **AI 客服旧依赖已从当前开发分支删除，但尚未部署。** 本分支移除了旧 `ai-support` Edge Function、前端气泡与后台配置组件；此前的 `https://api.meoo.host` 代码不应再作为独立站点功能使用。该删除随 PR 合并/部署前不会改变线上站点。
2. **用户名登录接口刚做了隐私加固，仍需部署与压力测试。** 当前开发分支的 `functions/login-lookup/index.ts` 不再把邮箱返回给浏览器，而是在服务端按用户名定位账号、调用 Supabase Auth 校验密码，只返回会话令牌；未知用户名、重名用户名与密码错误使用相同的通用失败响应。此改动仅在分支源码中，尚未部署到目标 Supabase。部署后仍需验证函数 secrets、GoTrue 限流、旧账号兼容性与登录回归。
3. **支付功能仍需要服务端密钥和真实验收。** `functions/alipay-pay/index.ts`、`functions/alipay-sweep/index.ts` 使用支付宝应用 ID、商户私钥和支付宝公钥等配置。只有在你自己的商户配置完成、签名/查单结果校验与订单状态更新通过沙箱测试后，才可开放在线支付。
4. **验证码和老板看板需要服务端配置。** `order-captcha` 使用 service-role 权限写入验证码挑战表；`boss-api` 需要独立口令和 Supabase 服务端密钥。所有这些值只能放在 Supabase Function secrets 中，绝不可放到浏览器变量。

## 独立商城改造新增迁移（2026-10-10）

本分支新增了三份增量迁移，**它们只能放在原始 schema 和所依赖的最终订单/卡密函数都已存在之后执行**。这不是首次初始化脚本，也不能代替对整套迁移链的核验：

1. `20261010_000100_independent_shop_auth_payment_audit.sql`
   - 为 `profiles.email` 补齐字段并从 Auth 用户回填；
   - 为 `orders` 增加 `payment_status` / `confirmed_at` 审计字段；
   - 创建管理员可访问的 `order_refunds` 审计表；
   - 补齐 Auth 新用户 profile 创建触发器及订单支付确认状态同步触发器。
2. `20261010_000200_order_assign_card_quantity.sql`
   - 覆盖最终版 `order_assign_card(TEXT)`，按订单购买数量一次性分配库存；
   - 库存不足时不消耗部分卡密，订单进入「已收款、待补发」状态；
   - 保留既有 `auto_whitelist_check` 调用和 RPC 签名。
3. `20261010_000300_auth_profile_username_conflict.sql`
   - 避免重复用户名的唯一约束冲突导致 Supabase Auth 注册失败；
   - 在用户名冲突时为新用户生成带用户 ID 后缀的唯一用户名。

这些迁移已提交到开发分支，但**尚未在可丢弃的 Supabase/PostgreSQL 数据库中执行**。上线前需要验证表/列/FK 与现有最终版函数兼容、迁移执行顺序、并发库存分配、库存不足回滚、重复支付回调幂等、Auth 注册用户名冲突和退款审计 RLS。若此前已经应用某个同名增量迁移，应先检查 schema 当前状态，避免重复执行不幂等 SQL。


## 2026-10-10 续：用户名登录隐私与管理员启用

- 开发分支已调整用户名登录协议：`functions/login-lookup` 接收用户名和密码，在服务端定位唯一 profile 后通过 Supabase Auth 验证凭据；返回 session token，不再返回账号邮箱。前端通过 `supabase.auth.setSession` 建立会话。
